# Compatibility policy

This page says what modelgen promises to keep stable, what a release may
change, and how the supported ODCS versions are handled.

## What is covered

- **CLI commands and flags.** `init`, `new`, `validate`, `gen`, `schema`,
  `sources`, `run` and `check`, with the flags listed in
  [Commands & Configuration](usage.md#commands).
- **Exit codes.** Their numbers and meanings are the table in
  [Exit codes](usage.md#exit-codes).
- **The JSON report.** The document `--format json` prints, described by
  `src/modelgen/schema/modelgen-report-v1.json` and versioned by its
  `schema_version` field.
- **Lint codes.** The rule codes in [Lint Rules](linting.md).
- **Python names.** Everything in `modelgen.__all__`, documented in
  [Python API](api.md).
- **The generated-file header.** The first line of every generated file:

    ```sql
    -- GENERATED by modelgen <version> from <contract name> <contract version>. Do not edit.
    ```

    ```yaml
    # GENERATED by modelgen <version> from <contract name> <contract version>. Do not edit.
    ```

    `<version>` is the installed modelgen version, so it changes on every
    release and every generated file changes with it. When the contract has
    no `version`, the ` <contract version>` part is left out.
- **The supported ODCS versions.** See [ODCS versions](#odcs-versions).

## What a release may change

- **Patch releases (0.x.Y)** never change anything covered above.
- **While the project is 0.x**, a minor release (0.X.0) may change covered
  behaviour only with a "Breaking Changes" entry in the changelog and, where
  feasible, after a deprecation warning that has shipped in at least one
  earlier minor release.
- **From 1.0** the project follows
  [Semantic Versioning](https://semver.org/): covered behaviour changes only
  in a major release.
- **Exit-code meanings and lint codes are never reused** for something else.
  A removed lint code is retired, not recycled.
- **The JSON report** gets a new `schema_version` for any incompatible
  change. Adding optional fields is compatible.

## ODCS versions

These `apiVersion` values are supported. Each is validated against its own
bundled schema.

- `v3.0.2`
- `v3.1.0`
- `v3.2.0`

These legacy values are deprecated:

- `v3.0.1`
- `v3.0.0`
- `v2.2.2`
- `v2.2.1`
- `v2.2.0`

A legacy version is still accepted and validated against the v3.0.2 schema.
Every command that loads the contract prints
`Warning: apiVersion <version> is deprecated and will stop being accepted in a later minor release. Supported: v3.0.2, v3.1.0, v3.2.0.`
on stderr, and `--format json` reports it as a `warning` issue with code
`odcs-version-deprecated` and pointer `/apiVersion`. The exit code is not
affected. Support will be removed in a later minor release.

A contract whose `apiVersion` is newer than the bundled schemas, such as
`v3.3.0`, is rejected as invalid (exit code 1) with
`unsupported apiVersion` and the list of supported versions in the message.

## Deprecations

A deprecation is announced in the changelog and by a warning on stderr when
the deprecated thing is used. While the project is 0.x, a deprecated feature
stays for at least one minor release before it is removed.
